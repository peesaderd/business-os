## Session: Post-Midnight Cleanup — Fallbacks Removed + Lifecycle Hooked (July 25)
**Time**: ~00:09-00:59 UTC | **Model**: opencode-go/deepseek-v4-pro

### What Was Fixed

#### 1. ALL Gemini Fallbacks Removed — Errors Now Raise Immediately
**User directive**: "ทำแบบนี้ดีใช่มั้ยครับ รอให้มันสเถียรแล้วค่อยใส่ Fallback จะดีกว่า" — Yes.

| Location | Old Behavior | New Behavior |
|---|---|---|
| `analyze_product()` (prompt_builder.py:58) | Default profile with generic fields | `RuntimeError("ERR_GEMINI_ANALYSIS_FAILED")` |
| Video prompt `product_demo` | Hardcoded "Establishing wide shot..." template | `RuntimeError("ERR_GEMINI_VIDEO_PROMPT_FAILED")` |
| Video prompt `usage` | "She naturally demonstrates..." template | `RuntimeError` with style logged |
| Video prompt person styles | "stands near product... gestures" template | `RuntimeError` with style logged |
| Unknown ugc_style | Silent generic action | `RuntimeError("ERR_UNKNOWN_UGC_STYLE")` |
| Legacy elif blocks (review/tabletop/unbox) | Dead code never reached | ❌ Removed entirely |

**Error Response Format**:
- 422: `{"detail": {"error_code": "ERR_*", "message": "...", "product": "..."}}`
- 500: `{"detail": {"error_code": "ERR_INTERNAL", "message": "...", "product": "..."}}`
- `app.py` /build endpoint: catches `RuntimeError` → 422, all else → 500
- All errors get `BUILD_BLOCKED` or `BUILD_FAILED` log entries in pm2

**Philosophy**: Degrade gracefully (show nice error to user) but NEVER silently produce garbage. Fallback should only come AFTER system is stable, for true external failures (network, quota), not to cover up bugs.

#### 2. Product Lifecycle — Fully Hooked
**Previously**: `touch_product()` existed but was NEVER called — lifecycle table empty.
**Now**: Hooked at 3 points in pipeline flow:

- `main.py` after prompt-builder success → `_touch_product()` with `analyzed` state
- `main.py` after full pipeline complete → `_touch_product()` with `content_created` state
- After AiToEarn post success → `_mark_product_posted()` with `posted` state

**Schema sync**: Fixed mismatch between `CREATE TABLE` (missing `category`, `latest_job_id` columns) and `touch_product()` function. Added via ALTER TABLE.

**Backfill**: 20 existing products from `pipeline_logs.db` backfilled into `product_lifecycle`.

**Lifecycle states**: `new` → `analyzed` → `content_created` → `posted`

### Files Modified

- `prompt-builder-service/app.py` — Error handling: RuntimeError→422, else→500 with error_code

## Session: TUS Product Tab — Search UX Fixes (July 25)
**Time**: ~01:31-01:53 UTC | **Model**: opencode-go/deepseek-v4-pro

### Context
User reported TUS Product tab loading slow. Root cause: API response 137KB due to `description_th` + `notes` fields (script data ~300B each, useless for list view). Fixed API to strip those fields — reduced to 51KB (62% faster).

Then user said search bar still causing issues ("สินค้าไม่โหลด"). Multiple rounds of debugging:

### What Was Fixed

#### 1. Slow Product List Load
- **Root cause**: `/products/list` returning `description_th` + `notes` (contains script hook/body/cta ~300B each)
- **Fix**: Strip those fields from list response in `main.py` — 137KB → 51KB, 162ms → 129ms
- HTML still 350KB (entire SPA inline) — deferred to larger refactor

#### 2. Removed "✕ ล้าง" and "🔍 ค้นหา" Buttons
- Old: 2 buttons outside search input — clicking "ล้าง" called `searchProducts()` → reload 50 products
- New: Inline ✕ inside input + Enter to search only
- Added `onSearchInputChange()` toggle ✕ visibility
- Added `clearProductSearch()` — just clears input + focus, NO reload

#### 3. clearProductSearch Bug — Grid Empty After Clear
- **Root cause**: `clearProductSearch()` checked `resultInfo.textContent.includes('กำลังค้นหา')` — but `resultInfo` was already updated to `'🔍 พบ X รายการ'` after search completed → condition NEVER matched → `loadAnalyzedProducts()` never called
- **Fix**: `clearProductSearch()` now calls `loadAnalyzedProducts()` unconditionally to restore full product list
- Search bar: input with inline ✕, Enter to search, ✕ to clear + reload full list

### Key Lessons
- UI rendering ≠ API problem — API was 161ms the whole time, real issue was 137KB payload + 350KB HTML
- Don't blame the button UI before checking if the underlying function actually fires
- `resultInfo` text content changes after search completes — can't rely on it for state checking
